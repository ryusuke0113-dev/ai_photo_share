# AI 向けコンテキスト

このプロジェクトで実装を行う AI は、作業の前に必ずこのファイルを読むこと。
詳細は各設計書を参照し、このファイルと設計書が食い違う場合は、作業を止めてユーザーに確認する。

## 1. アプリの概要

- 友人同士で旅行や日常の写真を見せ合う、インスタグラム風の写真共有アプリ
- ログインしたユーザーが「写真1枚 + 短いキャプション」を投稿する
- 投稿一覧・投稿詳細はログインなしで誰でも見られる
- 利用者は友人グループ程度の少人数。ローカル環境（自分の PC）で動けばよい

## 2. 技術スタック

| 項目 | 内容 |
| --- | --- |
| Python | 3.13.5（`.venv` を使用） |
| Web フレームワーク | Flask 3.1.3 |
| ORM | peewee 4.5.3 |
| データベース | SQLite（プロジェクト直下の `app.db`） |
| 環境変数 | python-dotenv 1.2.4（`.env` を Flask が自動で読み込む） |
| 見た目 | Bootstrap 5（`base.html` で CDN 読み込み） |
| ログイン管理 | Flask の `session`（Flask-Login は使わない） |
| 起動コマンド | `flask --app app run --debug` |

上記以外のパッケージは追加しない（Flask-Login、Flask-WTF、pytest なども使わない）。

## 3. ディレクトリ構成

```text
ai_photo_share/
├── app.py              # 設定・ルート・ログイン関連の処理
├── models.py           # データベース接続・モデル（User / Post / Like）
├── requirements.txt
├── .env                # SECRET_KEY（Git に含めない）
├── .gitignore
├── app.db              # 自動生成（Git に含めない）
├── uploads/            # アップロードされた写真（Git に含めない）
├── docs/
├── static/
│   └── css/
│       └── style.css   # Bootstrap で足りない部分だけ書く
└── templates/
    ├── base.html
    ├── index.html
    ├── post_detail.html
    ├── post_new.html
    ├── register.html
    └── login.html
```

**画像の保存先は、プロジェクト直下の `uploads/` である。`static/uploads/` ではない。**
写真は `/uploads/<filename>`（関数名 `uploaded_file`）で `send_from_directory` を使って返す。

## 5. 間違えやすい決まり

- 登録成功後は `/login` へ、ログイン・ログアウト・投稿・削除の成功後は `/` へリダイレクトする
- メールアドレスと表示名は、どちらも重複不可
- 表示名は 30 文字まで、キャプションは 140 文字まで（キャプションは空欄可）
- 写真は JPG・PNG のみ、5MB まで
- 投稿一覧は新しい順に縦1列で表示し、ページ分けはしない
- 削除ボタンといいねボタンは、投稿詳細画面にだけ置く（一覧には置かない）
- 削除できるのは投稿者本人のみ。他人の投稿の削除は 403
- 存在しない投稿は 404。404・403 は Flask 標準のエラー画面のままでよい
- 投稿日時は `2026年10月10日 14:30` の形で表示する
- CSRF 対策は今回は対象外

## 6. 今回作らないもの

## 7. AI の作業ルール

1. 1回の依頼では、`docs/tasks.md` のタスクを**1つだけ**実装する（ユーザーの指定がなければ、未完了の一番上のタスク）
2. 実装後は、次の3つを日本語で伝える
   - 変更・作成したファイル
   - 書いたコードの説明（初学者向けに、処理のまとまりごと）
   - ブラウザでの確認手順（`docs/tasks.md` の「確認」をもとにする）
3. ユーザーが「OK」と伝えたら、`docs/tasks.md` の該当タスクを `[x]` にする。それまでは `[ ]` のまま
4. ユーザーの指示なしに、次のタスクへ進まない
5. 設計書にない機能・画面・ルート・パッケージを追加しない。必要だと思った場合は、実装せずに提案してユーザーに確認する
6. 設計を変える必要がある場合は、先にユーザーに確認し、了承後に該当する設計書も更新する
7. コードは `docs/coding_rules.md` に従って書く
